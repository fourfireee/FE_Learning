# 前端架构与状态管理

- 前端架构的核心不是文件夹怎么分，而是数据怎么流动、状态放在哪里、边界怎么定义。
- 对编辑器类项目，状态设计会直接影响功能扩展、撤销重做、性能和调试难度。

- 常见状态类型：
    - 组件本地状态：只被一个组件使用，比如输入框是否展开。
    - 全局 UI（User Interface，用户界面）状态：多个组件共享，比如当前选中的节点。
    - URL（Uniform Resource Locator，统一资源定位符）状态：可以通过链接复现，比如当前 tab、搜索条件。
        - 「可以通过链接复现」指：把这部分状态写进 URL（路径或查询参数，如 `?tab=settings&q=cat`），状态就跟着链接走。别人打开同一个链接、自己刷新页面、收藏后再访问，都能回到完全一样的界面。
        - 好处：可分享、可收藏、刷新不丢、浏览器前进/后退能用。所以「希望别人通过链接就能看到同样画面」的状态，就适合放进 URL，而不是只存在内存里。
    - 服务端状态：来自接口的数据，比如 workflow 列表、模型列表。
    - 临时交互状态：拖拽中、框选中、连线中。

- 状态放置原则：
    - 谁需要读，状态就放在它们共同的最近上层。
    - 能由已有数据算出来的，不要重复存。
    - 需要持久化的状态要有明确 schema。schema 是数据结构约定，说明一个文件或对象应该有哪些字段、字段是什么类型。
    - 临时状态不要污染正式业务数据。
        - 临时状态：交互中的瞬时值，如「正在拖拽的位置」「框选范围」「悬停高亮」；业务数据：最终要保存的内容，如节点真实坐标、连线关系。
        - 「污染」即把临时值混进业务数据：比如拖拽时每帧都直接改节点真实坐标，于是未确认的中间态、甚至拖到一半取消的值都进了正式数据。
        - 危害：撤销重做塞满无意义的中间步；存盘存进脏数据；分不清「用户确认的结果」和「手还没松的过程值」。
        - 做法：拖拽时只更新一份独立的临时状态，等操作真正结束（松手/确认）再一次性写回业务数据。

- 编辑器状态可以拆成：
    - document state：文档状态，保存节点、边、参数。
        - 这里以「节点图（node graph）」编辑器为例——正是你要做的类 ComfyUI 的 AIGC workflow 工具的形态。
        - 节点（node）：图里的一个个方块，代表一步操作/一个模型；边（edge）：连接节点的连线，表示数据从一个节点流向另一个；参数（参数/parameter）：每个节点上可调的配置，如某模型的步数、强度。
        - 之所以是这三样，因为它们就是「文档」的本体：把节点、边、参数存下来，就能完整还原整张 workflow 图。其他编辑器（如画板）文档本体可能换成图层、形状，但思路一样——document state 存的是「最终要持久化的内容本身」。
    - selection state：选择状态，保存当前选中什么。
    - viewport state：视口状态，保存缩放、平移。
    - interaction state：交互状态，保存正在拖拽、正在连线。
    - history state：历史状态，保存 undo / redo 栈。

- undo / redo 的几种方式：
    - command 模式：记录每次操作和它的反操作。
    - patch 模式：记录每次变更的差异。
    - snapshot 模式：记录每次操作后的完整快照。

- 取舍：
    - command 模式表达力强，但实现复杂。
    - patch 模式适合结构化数据，存储成本较低。
    - snapshot 模式最容易理解，但大文档会占内存。

```js
const command = {
  do(state) {
    return addNode(state, { id: "node-1", x: 100, y: 100 });
  },
  undo(state) {
    return removeNode(state, "node-1");
  },
};
```

- 判断状态管理是否靠谱：
    - 是否能从状态直接还原界面。
    - 是否能解释一次用户操作改变了哪些状态。
    - 是否能撤销重做。
    - 是否能序列化保存。
    - 是否避免多个地方同时维护同一份事实。
